### 프롬프트 엔지니어링 시대

사람 → 프롬프트 → 모델 → 답변

## 하네스 엔지니어링

사람 → 목표 → 에이전트 → [도구 호출 → 판단 → 도구 호출 → 판단 → … ] → 결과

- 에이전트가 자율적으로 수십 ~ 수백 번 판단
- 모델이 뛰어나도 자율적 판단 횟수가 늘어나면 정확도 떨어짐

### 하네스
- Feedforward(사전 제어) - 틀릴 여지를 줄임
    - 맥락과 규칙 제시
    - 시스템 프롬프트, CLAUDE.md 등
    - 도구 정의와 제약 조건
    - 예시와 패턴 제공
    - 도로의 차선과 표지판 같은 역할
- Feedback(사후 제어) - 틀린 걸 바로 잡음
    - Computational(결정론적): 테스트, 린터, 타입 체커
    - Inferential(추론적): AI 코드 리뷰어, 품질 심사 에이전트
    - 자동차 차선 이탈 경고 시스템 같은 역할
- Guardrails(가드레일) - 넘으면 안되는 선
    - 파일 삭제 금지, 특정 API 호출 차단
    - 비용 한도, 시간 한도
    - 샌드박스 격리
    - 도로의 방호벽 같은 역할


### Keep Quality Left 원칙
- 하네스 설계의 핵심 철학
- 저렴하고 빠른 검증 <-> 비싸고 느린 검증
- 린터, 타입체커(pre-commit) - 테스트(pre-push) - 코드리뷰(pre-merge) - 프로덕션 모니터링(post-deploy)
- 가능한 왼쪽에서 문제 잡기

### Martin Fowler 프레임워크
| 카테고리     | 검증            | 성숙도            |
|----------|---------------|----------------|
| 유지보수성    | 코드 스타일, 구조 규칙 | 높음(린터 등 도구 성숙) |
| 아키텍처 적합성 | 성능, 설계 원칙     | 중간             |
| 동작 정확성   | 기능이 맞게 동작하나   | 낮음(가장 어려움)     |

- 동작 정확성: 비즈니스 요구사항 충족 판단
